# Критерії прийнятності для готовності до продакшну

Цей документ фіксує узгодження, що означає «готовість до продакшну» для
сервісу KDV Integrator. Він посилається в roadmap (M0) та використовується
рев’юерами релізів.

## 1. Обов’язкові сценарії
Кожен із перелічених сценаріїв має працювати без помилок перед тим, як ми
вважатимемо кандидат релізу готовим:

1. **Асинхронний запит інтеграції**
   ```bash
   curl -X POST \
        -H "X-KDV-TOKEN: $TOKEN" \
        https://integrator.example.com/kdv/api/integrate/12345678
   ```
   _Очікується:_ `202 Accepted` та JSON із полем `{"task_id":"<uuid>"}`.
   Повторні запити з тим самим бібліонумером у короткому інтервалі не повинні
   створювати дублікати задач (ідемпотентність).

2. **Опитування статусу**
   ```bash
   curl https://integrator.example.com/kdv/api/status/<task_id>
   ```
   _Очікується:_ `200 OK` з JSON на кшталт
   `{"status":"processing","result":{...}}`. Статус повинен переходити через
   `queued` → `processing` → (`success`|`error`).

3. **Поведение fork‑join**
   - Путь імпорту в DSpace має бути **критичним**; якщо DSpace падає, задача
     врешті-решт потрапляє в `error`, і файл не залишається в підвішеному стані.
   - Генерація/завантаження обкладинки є **best‑effort**: помилки логуються як
     `warning`, не припиняють задачу, і книга все одно імпортується.

4. **Файлова гігієна**
   - Оригінальні файли на монтованому диску перейменовуються перед обробкою
     (`foo.pdf` → `foo.pdf.processing`).
   - Після успішної обробки вони опиняються в `Processed/` із суфіксом-міткою часу.
   - У разі помилки файл переміщується до `Error/`, а статус задачі стає
     `error` з чітким повідомленням.

5. **Batch/robot/nightwalker**
   - `scripts/robot.py` успішно перебирає список бібліонумерів і ставить їх у чергу.
   - `scripts/nightwalker.py` виявляє сирітські файли/записи і або ставить їх
     у чергу знову, або звітує про них, не падаючи.

## 2. SLI / SLO
Показники рівня сервісу та цілі, які ми погодилися відстежувати щонайменше:

| Метрика                                 | Ціль SLO             |
|----------------------------------------|----------------------|
| Доступність API (за хвилину)           | ≥ 99.5 %             |
| p95 latency для `POST /integrate`      | < 500 мс             |
| Рівень помилок (4xx+5xx відповіді)      | < 1 %                |

Ці значення є прикладом і можуть коригуватися командою експлуатації під час
першого розгортання.

## 3. Критерії “stop‑ship”
Реліз НЕ МОЖЕ переходити в staging/prod, якщо в поточному кандидатові є будь‑який
з наведених дефектів:

- Запити інтеграції регулярно повертають `500` або втрачають `task_id`.
- Ендпоінт статусу повертає непослідовні або відсутні стани (наприклад, зависає
  в `processing` назавжди).
- Файли залишаються в корені монтованого диску без перейменування або
  перезаписуються.
- Критичний шлях DSpace виготовляє пошкоджені items або “dangling” handles.
- Скрипти batch robot/nightwalker падають або генерують фальшиві помилки великого
  обсягу.
- Секрети (наприклад, `KDV_API_TOKEN`) включені в клієнтський код (Koha JS).

Додаткові критерії stop‑ship можуть додаватися як issues у міру виявлення під
час раннього QA; поточний список — мінімальний погоджений набір.
